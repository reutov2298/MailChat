# Предложение: адаптер UT Telegraph (Telegra.ph)

**Статус:** предложение для исследования; реализация и пригодность транспорта не проверены.

## 1. Назначение

Рассмотреть Telegra.ph (https://telegra.ph/) как дополнительный транспортный адаптер UT наравне с Gmail. Его предполагаемая роль — передача небольших непрозрачных транспортных пакетов MC/UT через API публикации и чтения страниц.

Telegra.ph не рассматривается как почтовый сервис или защищённое хранилище. Страницы могут быть публично доступны по URL. Поэтому публикация допустима только для пакетов, которые уже зашифрованы и аутентифицированы на уровне MC/UT.

## 2. Предполагаемый API

Официальный Telegraph API предоставляет операции, представляющие интерес для прототипа:

- `createAccount` — создание аккаунта и получение access token;
- `createPage` — публикация страницы;
- `getPage` — чтение страницы;
- `getPageList` — получение списка страниц аккаунта;
- `editPage` — изменение страницы;
- `revokeAccessToken` — отзыв токена доступа.

Документация API указывает ограничение размера содержимого страницы. Точное полезное ограничение для транспортного пакета должно быть измерено с учётом кодирования, разметки и служебных данных.

## 3. Варианты организации обмена

### Вариант A. Анонимные страницы через веб-интерфейс

- Каждый клиент создаёт собственную страницу без регистрации.
- Получатель получает публичный URL страницы.
- Автор сохраняет локальное состояние, которое позволяет редактировать страницу; точный вид этого секрета и способ доступа из Android-приложения пока неизвестны.
- Получатель периодически читает страницу по URL и обнаруживает обновлённый пакет.
- Для двустороннего обмена каждый участник создаёт собственную страницу и передаёт её URL собеседнику.

Преимущество — не требуется создавать Telegraph account по пользовательскому сценарию сайта.

Критические вопросы: как безопасно и программно сохранить право редактирования; можно ли получить его при создании страницы без браузера; как передать первоначальный URL; как обнаруживать изменения без отдельного канала; есть ли API/HTTP-интерфейс для чтения и обновления таких страниц; не привязано ли редактирование к браузерному профилю.

### Вариант B. Общий API-аккаунт на пару участников

Оба клиента используют общий Telegraph account и его токен для публикации и обнаружения страниц.

Преимущества:
- потенциально позволяет обоим участникам публиковать пакеты в одном пространстве;
- получатель может обнаруживать новые страницы через список страниц аккаунта;
- не требуется передавать URL каждой новой страницы отдельным транспортом.

Риски и вопросы:
- общий токен является общей учётной сущностью и расширяет последствия его компрометации;
- необходимо проверить, могут ли оба клиента безопасно и корректно работать с одним токеном;
- нужно определить разграничение авторства, адресацию, конкурентную публикацию и удаление/изменение страниц;
- нельзя считать список страниц приватным каналом.

### Вариант B. Отдельный аккаунт каждого участника

Каждый клиент публикует страницы в собственном аккаунте. Получатель должен каким-либо способом узнавать адреса новых страниц.

Преимущества:
- нет общего токена на двоих;
- учётные данные каждого участника можно хранить и отзывать независимо.

Ограничение:
- требуется отдельный механизм обнаружения или передачи новых URL; без него этот вариант сам по себе не образует полноценный двусторонний транспорт.

Ни один из вариантов пока не выбран. В первую очередь следует исследовать анонимный веб-сценарий, который описал пользователь; API-аккаунты остаются альтернативой. Решение принимается после прототипирования и анализа безопасности.

## 4. Предполагаемый поток передачи

1. UT формирует транспортное задание и выбирает адаптер Telegraph.
2. На вход адаптера передаётся непрозрачный пакет, уже защищённый на уровне MC/UT.
3. Адаптер публикует пакет как страницу Telegraph и сохраняет полученный идентификатор/URL и результат операции.
4. На стороне получателя адаптер периодически проверяет доступный список страниц либо использует другой подтверждённый механизм обнаружения.
5. Адаптер загружает новые страницы и передаёт извлечённые пакеты в UT.
6. UT выполняет дедупликацию и передаёт пакет в MC; MC проверяет криптографическую подлинность и выполняет прикладную обработку.
7. Подтверждения доставки и обработки передаются отдельно и только на основании реально наблюдаемых событий.

Публикация страницы не означает, что пакет получен адресатом, принят UT или обработан MC.

## 5. Безопасность

- Запрещено публиковать открытый текст сообщений, приватные ключи, токены MC, секреты или персональные данные.
- Шифрование и криптографическая аутентификация выполняются до передачи данных адаптеру.
- Telegraph и его API рассматриваются как недоверенная внешняя инфраструктура.
- Access token Telegraph — секрет адаптера; его нельзя включать в пакет, журнал, диагностический отчёт или общедоступную страницу.
- Необходимо изучить последствия утечки URL, возможность подмены/удаления/изменения страниц и модель контроля доступа.
- Нельзя полагаться на URL как на единственный механизм аутентификации пакета.
- Компрометация или недоступность Telegraph не должна нарушать целостность данных MC/UT или блокировать работу других адаптеров.

## 6. Надёжность и эксплуатационные ограничения

До принятия решения необходимо экспериментально определить:

- фактические лимиты размера страниц и частоты API-запросов;
- задержку публикации и обнаружения новых страниц;
- поведение API при параллельных запросах и публикациях;
- доступность и стабильность списка страниц;
- срок хранения, редактирование и удаление страниц;
- обработку ошибок, rate limits и временной недоступности;
- ограничения условий использования и допустимость такого сценария;
- механизм подтверждений, повторов, дедупликации и очистки старых записей.

У API не следует предполагать наличие push-уведомлений или гарантированной доставки. Базовый прототип должен исходить из периодического опроса, пока обратное не будет подтверждено документацией и испытаниями.

## 7. План прототипирования

1. В обычном браузере создать тестовую страницу без регистрации.
2. Изучить cookies, local storage и сетевые запросы браузера до и после создания страницы; установить, где и в каком виде хранится право редактирования. Не публиковать и не передавать реальные секреты.
3. Проверить, можно ли прочитать страницу и изменить её из другого браузера/профиля с разными наборами cookies.
4. Проверить, можно ли безопасно реализовать создание, чтение и редактирование из Android-приложения без управления полноценным браузером.
5. Выяснить, существует ли поддерживаемый анонимный API или веб-endpoint, и оценить стабильность/условия его использования.
6. Отдельно проверить API-режим с access_token как резервный вариант.
7. Опубликовать только тестовый зашифрованный пакет; проверить двустороннюю передачу, обнаружение обновлений, дубликаты и повторы.
8. Измерить задержки, пропускную способность, лимиты и частоту ошибок.
9. Проверить последствия утечки URL, cookie и API-токена.
10. Подготовить отчёт и критерии допуска адаптера к каталогу UT.

## 8. Предварительная архитектурная позиция

Telegraph рассматривается как дополнительный независимый адаптер, а не как специальная логика MC. При этом анонимный веб-режим без регистрации и официальный API с account/access_token — два разных механизма, и их нельзя смешивать в реализации. UT в перспективе может отправлять один пакет через несколько доступных адаптеров и принимать ответ через любой доступный канал. Такая избыточная передача является отдельной политикой UT и требует правил дедупликации и подтверждений.

**До успешного прототипа Telegraph не считается поддерживаемым или надёжным транспортом.** Все описанные потоки — проектная гипотеза, а не реализованная функция.
