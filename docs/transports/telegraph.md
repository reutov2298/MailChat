# Предложение: адаптер UT Telegraph (Telegra.ph)

**Статус:** предложение для исследования; реализация и пригодность транспорта не проверены.

## 1. Назначение

Рассмотреть Telegra.ph (https://telegra.ph/) как дополнительный транспортный адаптер UT наравне с Gmail. Его предполагаемая роль — передача небольших непрозрачных транспортных пакетов MC/UT через API публикации и чтения страниц.

Telegra.ph не рассматривается как почтовый сервис или защищённое хранилище. Страницы могут быть публично доступны по URL. Поэтому публикация допустима только для пакетов, которые уже зашифрованы и аутентифицированы на уровне MC/UT.

## 2. Предполагаемый API

Официальный Telegraph API предоставляет операции, представляющие интерес для прототипа:

- `createAccount` — создание аккаунта и получение access token;
- `createPage` — публикация страницы;
- `getPage` — чтение страницы;
- `getPageList` — получение списка страниц аккаунта;
- `editPage` — изменение страницы;
- `revokeAccessToken` — отзыв токена доступа.

В официальной API-модели `createPage` и `editPage` требуют `access_token`; для `editPage` также нужен путь страницы (`path`). Чтение страницы через `getPage` возможно без токена, но сведения о возможности редактирования (`can_edit`) зависят от переданного токена.

Документация API: https://telegra.ph/api

Документация API описывает account/access_token-модель. Её нельзя автоматически считать описанием того, как работает анонимный редактор сайта.

Документация API указывает ограничение размера содержимого страницы. Точное полезное ограничение для транспортного пакета должно быть измерено с учётом кодирования, разметки и служебных данных.

## 3. Варианты организации обмена

### Вариант A. Анонимные страницы через веб-интерфейс

Пользовательский сценарий сайта позволяет открыть Telegra.ph, создать страницу без ручной регистрации и затем редактировать её. Это отдельный сценарий, который необходимо исследовать независимо от публично документированного API.

Предполагаемая модель:

- пользователь создаёт страницу без явного входа в аккаунт;
- сайт сохраняет локальное состояние, позволяющее автору редактировать страницу;
- получатель получает публичный URL страницы;
- получатель периодически читает страницу по URL и обнаруживает обновлённый пакет;
- для двустороннего обмена каждый участник создаёт собственную страницу и передаёт её URL собеседнику.

**Предварительные технические выводы (требуют проверки на актуальной версии сайта):**

- По имеющимся техническим описаниям, право редактирования анонимных страниц может храниться в `localStorage` сайта `telegra.ph` в виде `access_token` или связанного с ним секрета.
- Это не следует путать с cookie `tph_token` домена `edit.telegra.ph`, который относится к отдельному механизму авторизации/редактирования.
- Следовательно, первоначальное предположение, что право редактирования обычной анонимной страницы обязательно хранится в cookie, не подтверждено.
- Вероятная гипотеза: веб-интерфейс автоматически получает или создаёт технический токен и сохраняет его в локальном состоянии браузера. Не установлено, какой именно запрос выполняется, как формируется токен и совпадает ли он с токеном, получаемым через публичный `createAccount`.

Эти выводы пока не основаны на полном анализе актуального JavaScript и сетевого обмена сайта. Их нельзя считать установленным внутренним устройством сервиса.

**Возможность реализации в Android:**

1. Воспроизвести браузерную модель через WebView и его хранилище. Это может упростить совместимость, но создаёт зависимость от веб-интерфейса и требует безопасного обращения с локальным секретом.
2. Реализовать прямую работу через официальный API: создать технический Telegraph account методом `createAccount`, сохранить `access_token` в защищённом хранилище Android, затем выполнять публикацию и редактирование напрямую. Пользователю при этом не требуется вручную регистрироваться или работать с браузером.

**Предварительное предпочтение для прототипа:** сначала проверить прямой API-вариант. Он документирован, не требует автоматизации браузера и позволяет изолировать работу адаптера. Это не доказывает, что API-вариант полностью эквивалентен анонимному веб-сценарию или что он лучше по всем эксплуатационным параметрам.

Критические вопросы: можно ли безопасно и программно получить право редактирования анонимной страницы; как именно веб-интерфейс хранит и использует секрет; можно ли воспроизвести этот сценарий из Android без браузера; можно ли использовать API account/access_token как автономную альтернативу; как передать первоначальный URL; как обнаруживать изменения без отдельного канала.

### Вариант B. Общий API-аккаунт на пару участников

Оба клиента используют общий Telegraph account и его токен для публикации и обнаружения страниц.

Преимущества:
- потенциально позволяет обоим участникам публиковать пакеты в одном пространстве;
- получатель может обнаруживать новые страницы через список страниц аккаунта;
- не требуется передавать URL каждой новой страницы отдельным транспортом.

Риски и вопросы:
- общий токен является общей учётной сущностью и расширяет последствия его компрометации;
- необходимо проверить, могут ли оба клиента безопасно и корректно работать с одним токеном;
- нужно определить разграничение авторства, адресацию, конкурентную публикацию и удаление/изменение страниц;
- нельзя считать список страниц приватным каналом.

### Вариант C. Отдельный API-аккаунт каждого участника

Каждый клиент публикует страницы в собственном аккаунте. Получатель должен каким-либо способом узнавать адреса новых страниц.

Преимущества:
- нет общего токена на двоих;
- учётные данные каждого участника можно хранить и отзывать независимо.

Ограничение:
- требуется отдельный механизм обнаружения или передачи новых URL; без него этот вариант сам по себе не образует полноценный двусторонний транспорт.

Ни один из вариантов пока не выбран. Для первого прототипа предлагается проверить прямой официальный API (вариант B или C), а анонимный веб-сценарий исследовать отдельно. Окончательное решение принимается после прототипирования и анализа безопасности.

## 4. Предполагаемый поток передачи

1. UT формирует транспортное задание и выбирает адаптер Telegraph.
2. На вход адаптера передаётся непрозрачный пакет, уже защищённый на уровне MC/UT.
3. Адаптер публикует пакет как страницу Telegraph и сохраняет полученный идентификатор/URL и результат операции.
4. На стороне получателя адаптер периодически проверяет доступный список страниц либо использует другой подтверждённый механизм обнаружения.
5. Адаптер загружает новые страницы и передаёт извлечённые пакеты в UT.
6. UT выполняет дедупликацию и передаёт пакет в MC; MC проверяет криптографическую подлинность и выполняет прикладную обработку.
7. Подтверждения доставки и обработки передаются отдельно и только на основании реально наблюдаемых событий.

Публикация страницы не означает, что пакет получен адресатом, принят UT или обработан MC.

## 5. Безопасность

- Запрещено публиковать открытый текст сообщений, приватные ключи, токены MC, секреты или персональные данные.
- Шифрование и криптографическая аутентификация выполняются до передачи данных адаптеру.
- Telegraph и его API рассматриваются как недоверенная внешняя инфраструктура.
- Access token Telegraph — секрет адаптера; его нельзя включать в пакет, журнал, диагностический отчёт или общедоступную страницу.
- Токены и секреты браузерного хранилища нельзя помещать в логи, резервные копии без защиты или передавать получателю.
- Необходимо изучить последствия утечки URL, возможность подмены/удаления/изменения страниц и модель контроля доступа.
- Нельзя полагаться на URL как на единственный механизм аутентификации пакета.
- Компрометация или недоступность Telegraph не должна нарушать целостность данных MC/UT или блокировать работу других адаптеров.

## 6. Надёжность и эксплуатационные ограничения

До принятия решения необходимо экспериментально определить:

- фактические лимиты размера страниц и частоты API-запросов;
- задержку публикации и обнаружения новых страниц;
- поведение API при параллельных запросах и публикациях;
- доступность и стабильность списка страниц;
- срок хранения, редактирование и удаление страниц;
- обработку ошибок, rate limits и временной недоступности;
- ограничения условий использования и допустимость такого сценария;
- механизм подтверждений, повторов, дедупликации и очистки старых записей.

У API не следует предполагать наличие push-уведомлений или гарантированной доставки. Базовый прототип должен исходить из периодического опроса, пока обратное не будет подтверждено документацией и испытаниями.

## 7. План прототипирования

1. В обычном браузере создать тестовую страницу без регистрации.
2. Изучить актуальный JavaScript редактора и сетевые запросы до и после создания страницы; установить, какой запрос создаёт/получает право редактирования и где хранится соответствующий секрет.
3. Проверить, какие данные сохраняются в `localStorage`, cookies и других хранилищах; не публиковать и не передавать реальные секреты.
4. Проверить чтение и редактирование тестовой страницы из другого браузера/профиля с разными наборами cookies и local storage.
5. Отдельно проверить официальный API: создать тестовый account через `createAccount`, сохранить токен, выполнить `createPage`, `getPage`, `getPageList`, `editPage` и отзыв токена.
6. Сравнить анонимный веб-сценарий и API-сценарий: модель доступа, возможность восстановления, ограничения, стабильность и соответствие условиям использования.
7. Проверить, можно ли безопасно реализовать выбранный сценарий непосредственно в Android без управления полноценным браузером.
8. Опубликовать только тестовый зашифрованный пакет; проверить двустороннюю передачу, обнаружение обновлений, дубликаты и повторы.
9. Измерить задержки, пропускную способность, лимиты и частоту ошибок.
10. Проверить последствия утечки URL, cookie, local storage и API-токена.
11. Подготовить отчёт и критерии допуска адаптера к каталогу UT.

## 8. Предварительная архитектурная позиция

Telegraph рассматривается как дополнительный независимый адаптер, а не как специальная логика MC. Анонимный веб-режим без ручной регистрации и официальный API с account/access_token — два разных сценария, и их нельзя смешивать в реализации. При этом веб-интерфейс может автоматически использовать технические учётные данные; это необходимо подтвердить анализом реального сетевого обмена.

Для первого технического прототипа предпочтительно проверить прямой официальный API с отдельным техническим аккаунтом и защищённым хранением токена на устройстве. Параллельно можно исследовать анонимный веб-механизм, но не следует строить production-реализацию на недокументированных endpoint или предположениях о браузерном хранилище.

UT в перспективе может отправлять один пакет через несколько доступных адаптеров и принимать ответ через любой доступный канал. Такая избыточная передача является отдельной политикой UT и требует правил дедупликации и подтверждений.

**До успешного прототипа Telegraph не считается поддерживаемым или надёжным транспортом.** Все описанные потоки — проектная гипотеза, а не реализованная функция.
