# MC — Android application 1.1.10

Тестовая сборка MC для Android. Application ID: `ru.mailchat.app`; versionCode: `43`; versionName: `1.1.10`.

## Что изменено в 1.1.10

### Обработка удаления писем Gmail

- Gmail History запрашивает события добавления, окончательного удаления и добавления системной метки `TRASH`.
- Если письмо удалено или перемещено пользователем в корзину до синхронизации, его Gmail ID не передаётся на загрузку MIME и фиксируется как разрешённое событие удаления.
- Если пользователь переместил письмо в корзину уже после ответа History API, но до batch-загрузки, MC проверяет системную метку `TRASH` в ответе `messages.get` и пропускает импорт такого письма.
- Если письмо исчезло между получением списка ID и загрузкой, оно считается удалённым только при подтверждённом HTTP 404 соответствующего batch-подзапроса.
- Неполный batch-ответ, сетевые ошибки, HTTP 401/403/429 и серверные ошибки не трактуются как удаление; очередь остаётся незавершённой, а History cursor не продвигается.
- Если пользователь удалил письмо после загрузки, но до установки метки MC, HTTP 404 при изменении меток принимается как подтверждённое удаление. Уже сохранённая локальная копия MC сохраняется.
- Удаление письма в Gmail не удаляет сообщение из локальной переписки MC.
- Одновременное наличие одного ID в событиях добавления и удаления разрешается в пользу удаления; ID не загружается повторно.
- В логах фиксируются ID удалённых писем, количество запрошенных/полученных/удалённых ID и примеры оставшихся необработанных ID. Тексты писем и OAuth-токены не логируются.
- Добавлена отдельная чистая политика обработки History ID, покрытая модульными тестами для одиночного, массового и полного удаления, HTTP 404, временных ошибок и продвижения cursor.

## Что изменено в 1.1.9

### Надёжность Gmail History и повторная обработка

- Полученные из Gmail History ID сохраняются в отдельную локальную очередь для каждого Gmail-аккаунта до завершения обработки.
- History cursor продвигается только когда очередь потенциально входящих сообщений полностью разрешена.
- Письмо с признаками MC, которое не прошло разбор или проверку, не помечается обработанным; синхронизация завершается ошибкой и повторяет попытку, сохраняя прежний cursor.
- Обычные письма, достоверно не относящиеся к MC, отмечаются как пропущенные, чтобы не блокировать History cursor.
- Gmail ID, которые уже отсутствуют в Gmail (внутренний HTTP 404 при загрузке), считаются разрешёнными удалёнными событиями.
- Локальное сохранение переписки и отметка обработанного Gmail ID выполняются синхронно через SharedPreferences commit до продвижения cursor.
- Повторная обработка проверяет существующие MC messageId и messageVersion; повторное получение не создаёт дубликаты.
- При исключениях проверки записывается тип, безопасное диагностическое сообщение и ограниченный stack trace без содержимого письма и секретов.
- Повторные попытки проверки ошибочного MC-сообщения используют сохраняемый экспоненциальный backoff от 30 секунд до 6 часов; состояние переживает перезапуск приложения.
- Временные сетевые ошибки повторяются для идемпотентных GET-запросов и read-only Gmail batch-запросов. Запрос отправки письма автоматически не повторяется после неоднозначной сетевой ошибки, чтобы не создавать дубликаты.
- Диагностика отдельно показывает наличие подписи в MIME-заголовке и в необязательном видимом блоке MC DATA; дополнительно фиксируются MIME-типы и размеры структуры письма.
- Фоновая и ручная синхронизация используют одинаковое правило: не продвигать cursor при необработанном MC-сообщении.

## Что изменено в 1.1.8

### Отображение технической информации в письме

- В настройках добавлен флажок «Показывать техническую информацию в письме»; по умолчанию он снят.
- При включённом флажке тело письма содержит сначала пользовательский текст, затем блок `BEGIN/END MC DATA`.
- При выключенном флажке тело письма содержит только пользовательский текст.
- Протокольные поля MC, включая `X-MC-Text-Base64`, всегда передаются в MIME-заголовках независимо от настройки.
- Получатель обрабатывает сообщения по MIME-заголовкам; видимый блок в теле необязателен. Сохраняется совместимость со старыми письмами, в которых технический блок присутствует в теле.
- При наличии блока его значения сверяются с MIME-заголовками; расхождения приводят к отклонению письма.

## Что изменено в 1.1.7

### Gmail transport and synchronization

- Основная синхронизация переведена на Gmail API `users.history.list`: приложение получает идентификаторы новых сообщений после сохранённого `historyId`, а не выполняет повторный поиск по всему временному диапазону.
- Полный MIME-контент запрашивается только для новых Gmail ID, которых ещё нет в локальном списке обработанных. Это правило действует и для восстановительного поиска: он постраничный, а обработанные ID исключаются до загрузки MIME-контента.
- Batch-загрузка ограничена небольшими группами сообщений, чтобы уменьшить пиковую нагрузку.
- `historyId` и ID метки MC хранятся отдельно для каждого Gmail-аккаунта. `historyId` сохраняется только после успешной обработки набора. При HTTP 404 (устаревшая история) используется постраничный восстановительный поиск по прежней контрольной дате; после него сохраняется новая точка истории.
- Первое подключение сохраняет текущую точку Gmail History и не импортирует старую почту. Для аккаунтов, уже подключённых до обновления, первый запуск выполняет однократную миграционную выборку по прежней временной контрольной точке.
- HTTP 429 и распознаваемые quota/rate-limit ответы HTTP 403 повторяются с экспоненциальной задержкой и случайным разбросом; если сервер присылает `Retry-After`, задержка учитывает это значение. Ошибки авторизации HTTP 401 по-прежнему обрабатываются обновлением OAuth-токена.
- Повторные запросы ручной синхронизации объединяются: во время активной синхронизации допускается не более одного дополнительного цикла.
- Foreground и WorkManager используют общий локальный lock.

### Gmail label MC

- При подключении аккаунта приложение проверяет наличие метки `MC` и создаёт её, если она отсутствует.
- После проверки подписи и сохранения входящего сообщения в локальную базу приложение добавляет метку `MC` и удаляет системные метки `INBOX` и `SPAM`.
- Успешно отправленные письма MC получают метку `MC`; системная метка `SENT` сохраняется.
- Письма не перемещаются в корзину и не удаляются автоматически.
- Если пользователь удалит метку `MC`, приложение обнаружит невалидный label ID при следующем изменении сообщения, создаст метку заново и сохранит новый ID.
- Обычные письма, не прошедшие проверку MC, не архивируются и не получают метку MC.

### Gmail conversation threads

- При отправке MC формирует RFC-заголовок `Message-ID`; при ответе добавляет `In-Reply-To` и `References` на последнее известное сообщение диалога.
- Если для текущего аккаунта уже известен Gmail `threadId`, он передаётся в запрос отправки.
- `threadId` и последний RFC Message-ID хранятся отдельно для каждого почтового аккаунта и диалога.
- Входящие сообщения обновляют локальную привязку к Gmail Thread.
- Если Gmail не принимает сообщение в существующую цепочку, это не должно отменять саму отправку MC.

### Local state and safety

- Локальная база MC остаётся основным хранилищем переписок.
- Gmail ID исходящего сообщения помечается обработанным, чтобы синхронизация не пыталась импортировать собственное письмо обратно как входящее.
- Входящее сообщение сначала сохраняется локально, затем маркируется в Gmail и только после этого отмечается обработанным.
- OAuth scopes не расширялись: используются уже существующие `gmail.modify` и `gmail.send`.
- OAuth-токены, подписи и содержимое переписки не должны попадать в диагностические логи.

## Известные ограничения

- Gmail может объединить сообщения в цепочку только при соблюдении собственных правил threading (совпадающая тема, корректные RFC-заголовки и локальный для аккаунта threadId). Поэтому группировка гарантируется приложением как best effort, а не для каждого внешнего почтового клиента.
- Миграционная и восстановительная выборка пока ограничена 50 кандидатами за один запрос; это сохраняет прежнее ограничение прототипа. При очень большом накопившемся объёме писем может потребоваться несколько циклов или отдельная постраничная миграция.
- SharedPreferences JSON пока остаётся локальным хранилищем; Room не внедрён.
- Подтверждения доставки ACK и двух галочек пока нет. Состояние отправки в Gmail не является подтверждением получения сообщения адресатом.
- FCM, Gmail Watch, Pub/Sub и Cloud Functions не настроены.
- WorkManager ограничивает периодическую задачу минимум 15 минутами; при открытом приложении работает отдельная foreground-проверка.
- Первый контакт использует TOFU для публичного ключа. Ed25519 подтверждает целостность относительно полученного ключа, но сам по себе не подтверждает личность владельца Gmail-адреса.
- Текст сообщения не зашифрован сквозным шифрованием. Не использовать тестовую версию для конфиденциальной переписки.

## Rejected incoming MC messages and support diagnostics (1.1.11)

- A message recognized as MC but rejected by local protocol or cryptographic verification is not inserted as a normal chat message.
- The sender's chat receives a durable warning entry showing the reason, stable error code and Gmail message ID. If the sender address cannot be extracted, the entry is placed in the local **Ошибки обработки** chat.
- The entry has a **Скопировать для техподдержки** action. The copied report contains the error code, human-readable reason, Gmail ID and bounded technical diagnostics. It does not contain the message body, OAuth tokens, private keys, raw public keys or raw signatures.
- The Gmail ID is recorded in a separate per-mailbox rejected/quarantine set, the warning entry is persisted, and only then is the ID marked processed and removed from the pending queue. Repeated processing is idempotent.
- Local verification failures (malformed Base64, missing/invalid fields, unsupported protocol values, invalid public key or failed Ed25519 signature) are terminal rejections. Gmail API, network and storage failures remain retryable and continue to block cursor advancement until resolved.
- MIME transport whitespace (space, tab, CR and LF) is removed only inside Base64-encoded transport fields. The field-specific alphabet and padding are validated before decoding. Canonical signed content is not normalized or weakened.
- Manual and WorkManager synchronization use the same rejection and quarantine behavior.

### Test checklist for 1.1.11

1. Valid Base64 public key, signature, text and profile fields still verify.
2. MIME folding in Base64 fields is normalized without changing the signed canonical payload.
3. Illegal alphabet characters, impossible Base64 lengths and invalid padding are rejected with a field-specific diagnostic.
